# Resource budget

The single source of truth for every bound in this table is
`components/mtek_schema/include/mtek_schema_constants.h`, generated by
`tools/gen_schema.py` from `schemas.json`. This document is a
human-readable index into it, plus the additional, implementation-level
bounds this session introduced for the primitives `schemas.json` does not
itself define (the async delivery queue, native reassembly). Never
hand-edit a `MTK_BUDGET_*` value here without regenerating the schema
first -- this file must never drift from the generated header.

## Canonical core budgets (from `schemas.json`)

Runtime reliability maintenance adds one 4096-byte `mtek_delivery` task
stack, plus its FreeRTOS task-control block, to isolate capture deadlines
and 500ms GATT delivery from blocking BLE sampling. Capture is serviced
every 10ms rounded to at least one RTOS tick. Native SPI reassembly now
expires after 2000ms without an accepted fragment, including while the
master is silent; this is a local timeout policy, not a negotiated wire
parameter. Task stack/heap high-water measurements still require hardware.

| Budget | Value | Meaning |
|---|---|---|
| Max in-flight requests | 4 | `MTK_BUDGET_MAX_INFLIGHT_REQUESTS` |
| Max reassembly contexts | 4 | `MTK_BUDGET_MAX_REASSEMBLY_CONTEXTS` -- shared budget every over-one-cell control response draws from |
| Max control payload | 65,536 bytes | `MTK_BUDGET_MAX_CONTROL_PAYLOAD_BYTES` -- the logical (reassembled) message ceiling |
| Max operation tokens | 8 | `MTK_BUDGET_MAX_OPERATION_TOKENS` |
| Terminal event reserve | 0 | `MTK_BUDGET_TERMINAL_EVENT_RESERVE` -- the dedicated non-starvable runtime reserve is retired; terminal events (`*_STOPPED` / `*_COMPLETE`) share the best-effort priority queue with progress events, without a dedicated delivery guarantee. `GET_LIMITS.max_terminal_event_reserve` now reports 0 to match the implemented behavior rather than advertising a guarantee the firmware does not provide. |
| Max progress event queue | 8 | `MTK_BUDGET_MAX_PROGRESS_EVENT_QUEUE` |
| Max active cursors | 4 | `MTK_BUDGET_MAX_ACTIVE_CURSORS` |
| Max owned buffers | 4 | `MTK_BUDGET_MAX_OWNED_BUFFERS` |
| Operation record retention | 60,000 ms | `MTK_BUDGET_OPERATION_RECORD_RETENTION_MS` |
| GATT max subscriptions/connection | 16 | `MTK_BUDGET_GATT_MAX_SUBSCRIPTIONS_PER_CONNECTION` |
| Capture record max bytes | 1000 | `MTK_BUDGET_CAPTURE_RECORD_MAX_BYTES` |
| Beacon max SSIDs (canonical) | 32 | `MTK_BUDGET_BEACON_MAX_SSIDS_CANONICAL` |
| Probe-flood max SSIDs | 16 | `MTK_BUDGET_PROBE_FLOOD_MAX_SSIDS` |
| Raw TX frame bytes | 10..1489 | `MTK_BUDGET_RAW_TX_FRAME_MIN/MAX_BYTES` |
| Captive portal max credentials | 32 | `MTK_BUDGET_CAPTIVE_PORTAL_MAX_CREDENTIALS` |

## Transport-level budgets (this implementation, not schema-generated)

| Budget | Value | Where |
|---|---|---|
| Native SPI v1 cell size | 1024 bytes | `MTK_SPI_NATIVE_CELL_SIZE` |
| Native SPI v1 single-cell payload | 984 bytes | `MTK_SPI_NATIVE_MAX_PAYLOAD` |
| Native SPI v1 reassembled message ceiling | 8,192 bytes | `MTK_SPI_NATIVE_MAX_MESSAGE` -- **RC7: reduced from 65,536, a documented contract exception; see "RC6 measured SRAM conflict" below.** |
| Native SPI v1 reassembly abandonment threshold | 2000 (caller `now_seq` units) | `MTK_SPI_NATIVE_REASM_TIMEOUT_SEQ` -- a placeholder; real tuning needs hardware timing evidence not available this session, see `docs/PROVENANCE.md` |
| Native SPI v1 concurrent inbound reassembly contexts | 1 | `mtk_spi_native_dispatch_ctx_t::inbound` -- **RC7: a second contract exception; see below.** A FIRST fragment for a different request_id while one is in progress is rejected `LINK_ERROR`/`MTK_STATUS_BUSY` (`MTK_SPI_REASM_BUSY`), never silently overwritten. |
| Native SPI v1 concurrent DISPATCHED (already-received) operations | 4 | `MTK_SPI_NATIVE_MAX_IN_FLIGHT`, `mtk_spi_native_pending_t pending[4]` -- unaffected by either exception above: these are small correlation records (no bulk buffer), tracking operations the router has already accepted and is awaiting async completion for, matching the core contract's 4-in-flight budget exactly |

| Async delivery frame body | 960 bytes | `MTK_ASYNC_FRAME_MAX_BODY` |
| Router async pool size | 4 | `MTK_ROUTER_ASYNC_POOL_SIZE` (`mtek_router.c`) -- matches the 4-in-flight-request core budget above |
| Router async pool per-request payload cap | 2048 bytes | `MTK_ROUTER_ASYNC_MAX_PAYLOAD` |

## RC6 measured SRAM conflict (RC7 independent audit P0 "Target stack usage
is catastrophically larger than the configured stacks")

**The stack-overflow half (fixed unconditionally, no exception needed):**
`mtk_spi_native_dispatch_ctx_t`/`mtk_compat_dispatch_ctx_t` (`main/
mtek_spi_runtime.c`'s `spi_runtime_task`), `mtk_uart_adapter_state_t`/the
4KB output buffer (`main/app_main.c`'s `uart_repl_task`), and every
`uart_capture_t` local in `mtek_transport_uart/mtek_uart_adapter.c` (~25
call sites, several declaring two at once) were stack-local against 8KB
configured task stacks -- independently measured by the RC6 audit at a
152,688-byte required stack frame for `spi_runtime_task` alone. All are
now `static`, not stack-local (each task is a single, never-returning
boot-session singleton, so static storage has the same lifetime a
stack-local would have needed, without counting against the configured
stack at all). Both task stacks were also bumped (8192 -> 12288) as a
measured-safer starting point for what genuinely remains on them; the
real per-transaction/per-command high-water mark
(`uxTaskGetStackHighWaterMark`) still needs hardware measurement (no
target access this session) and is a disclosed gap, not a claimed-safe
number.

**The SRAM-budget half (a real, measured, documented contract exception):**
even after every structure above was moved off the stack, real `idf.py
size` output against this exact target/sdkconfig showed the shared
internal SRAM region ESP-IDF calls "DIRAM" -- which backs every static
`.bss`/`.data` allocation AND every FreeRTOS runtime heap allocation
(task stacks, `esp_wifi_init`, the NimBLE BLE stack, lwIP, NVS) --
totals 452,112 bytes, of which the pre-exception build already consumed
441,154 bytes (97.6%) before counting a single byte of runtime heap,
leaving only 10,958 bytes free:

```
DIRAM               441154    97.58     10958        452112
   .bss              297600    65.82
```

`riscv32-esp-elf-nm --size-sort` on the linked ELF identified the
dominant contributor: `native_dctx` (the `mtk_spi_native_dispatch_ctx_t`
singleton in `mtek_spi_runtime.c`) alone was 204,792 bytes -- three
independent 65,536-byte arrays (`inbound.data`, `outbound.data`, and
`sync_capture.body`, the last added by this same RC6 round to fix the
stack-overflow half above) plus the accepted contract's own 4-context
in-flight guarantee (`002-canonical-core-contract.md` Sec 6) would have
required *multiplying* the inbound buffer alone to 262,144 bytes --
already over half this chip's total DIRAM before any WiFi/BLE/FreeRTOS
allocation.

Per the RC7 correction order's own explicit instruction ("If the accepted
4x65,536-byte reassembly guarantee cannot fit, report the measured
conflict and proposed contract exception before changing the protocol"),
two exceptions are made here, both scoped to native SPI v1 specifically
(this tree's own List B / future-facing transport, `docs/ARCHITECTURE.md`
-- not a frozen List A shipped-parity surface, so it carries design
freedom the accepted contract itself grants):

1. **`MTK_SPI_NATIVE_MAX_MESSAGE` reduced from 65,536 to 8,192 bytes.**
   Independently checked against every message this codebase actually
   constructs on this transport: `AP_SCAN_RESULTS_PAGE`'s 50-record page
   is ~2.2KB; the largest EVENT/STREAM payload relayed through the same
   outbound path is ~985 bytes; nothing else in this tree legitimately
   needs more. The canonical schema-level `MTK_BUDGET_MAX_CONTROL_
   PAYLOAD_BYTES=65536` bound above is unchanged -- it still governs
   individual schema field lengths elsewhere (GATT read's
   `bytes(max=512)`, the capture record's `bytes(max=1000)`); this is
   specifically native SPI v1's own multi-cell reassembly/outbound/
   sync-capture buffer sizing, not a canonical contract change.
2. **Native SPI v1 keeps exactly ONE full-size inbound reassembly
   context, not the accepted four.** A second logical message's FIRST
   fragment arriving while one is still mid-reassembly is rejected
   explicitly (`MTK_SPI_REASM_BUSY` -> wire `LINK_ERROR`/
   `MTK_STATUS_BUSY`) rather than silently overwritten -- fixing the
   original defect (silent cross-message corruption) without requiring
   4x the buffer. The DISPATCH-level 4-in-flight guarantee (`pending[4]`,
   tracking already-fully-received operations awaiting async completion)
   is untouched and still exactly 4, since those records are small
   scalars with no bulk buffer -- see `test_spi_native_4inflight.c`.

**Measured result** (`idf.py size`, same target/sdkconfig, after both
exceptions plus the stack-overflow fixes above):

```
DIRAM               269122    59.53    182990        452112
   .bss              125568    27.77
```

172,032 bytes of DIRAM recovered; free headroom for runtime heap up from
10,958 to 182,990 bytes. `tools/check_resource_budget.py` mechanically
enforces a documented 100,000-byte minimum free-DIRAM floor against any
future build's own `idf.py size` output (RC6 independent audit gate #2
"published and mechanically checked in CI/build scripts") -- run it after
`idf.py build`, from the same `export.sh`-sourced shell:
`python3 tools/check_resource_budget.py build/mtkcore.map`. `mtk_spi_
native_dispatch_ctx_t`, `mtk_compat_dispatch_ctx_t`, and `mtk_uart_
adapter_state_t` each also carry a `_Static_assert` on their own
`sizeof` (their own header files) as a second, compiler-level regression
guard independent of any target build.

**What this does NOT claim**: a measured, bounded static-allocation
budget is not the same as a hardware-verified successful boot. Real
WiFi/BLE/FreeRTOS runtime heap consumption at startup has not been
measured on real hardware this session (no target access) --
`uxTaskGetStackHighWaterMark`/`esp_get_free_heap_size` results after an
actual boot remain a disclosed, hardware-only gap (`docs/PROVENANCE.md`),
not a claimed-safe number.

## RC7 follow-on: UART capture-buffer sharing (found while fixing P0 #2)

Implementing real cross-transport AUTO selection (below) required the
factory UART REPL task to start unconditionally instead of being
`#if`'d out whenever SPI was the build-time "primary transport" -- which
meant `mtek_uart_adapter.c`'s ~25 per-call-site `static uart_capture_t`
locals (RC6's own stack-overflow fix, each ~4.1KB) were compiled in and
counted against DIRAM for the first time. Measured impact: DIRAM used
jumped from 269,122 to 401,256 bytes (88.8%), free dropped from 182,990
to 50,856 -- below `tools/check_resource_budget.py`'s own 100,000-byte
floor, caught immediately by that mechanical gate.

Since the same single-threaded/non-reentrant argument that justified
`static` in RC6 applies equally to SHARING one instance across every
call site (this REPL never runs two commands concurrently), the ~25
independently-named statics were consolidated to exactly 3 shared
file-scope instances (the real maximum ever simultaneously live in one
call -- no handler needs more than two). Measured result: DIRAM used
301,608 bytes (66.7%), free 150,504 bytes -- comfortably over the floor,
with both UART and SPI adapters now compiled AND started concurrently
(see "RC7: real cross-transport AUTO selection" below).

## RC7: real cross-transport AUTO selection

RC6's `MTEK_PRIMARY_TRANSPORT` Kconfig choice picked exactly one of
UART/SPI to ever start at boot -- the RC7 independent audit found this
directly contradicts `SPI_PROTOCOL_V1.md`'s own "Runtime transport
selection" (AUTO discovery across a native SPI HELLO, a Mtek Compatibility/C3
discovery frame, OR a valid legacy UART command). That Kconfig choice is
removed; every compiled adapter (`CONFIG_MTEK_ADAPTER_*`) now starts its
own physical loop unconditionally, and `mtk_transport_claim_try`
(`components/mtek_transport_select/include/mtek_transport_select.h`) is
the real cross-transport exclusivity latch each one races the first time
it sees genuine protocol traffic on its own bus -- exactly one wins and
may ever reach `mtk_router_dispatch` for the rest of the boot session.
See `docs/DECISION_LOG.md`'s own RC7 entry for the full rationale and
`test_transport_claim.c` for the primitive's own single-threaded and
real-pthread-race test coverage. The two DIRAM measurements above are
this decision's own real cost accounting, not a separate one.

## RC7 follow-on: native SPI discovery cell-size negotiator extraction

Extracting the discovery cell-size upgrade timing fix (RC6 independent
audit P0 "Native 512-to-1024 discovery transition is still wrong" --
see `docs/DECISION_LOG.md`'s own entry) into a standalone
`mtk_native_cellsize_negotiator_t` in `components/mtek_transport_select`
replaced a single inline `int` local in `main/mtek_spi_runtime.c` with a
tiny struct plus three function calls. Measured impact: DIRAM used
301,896 bytes (66.8%, up 288 bytes from the prior 301,608), free 150,216
bytes -- still comfortably over `tools/check_resource_budget.py`'s
100,000-byte floor. Two independent clean `idf.py build` runs produced
byte-identical `mtkcore.bin` (SHA-256 match), confirming this measurement
is deterministic, not incidental.
